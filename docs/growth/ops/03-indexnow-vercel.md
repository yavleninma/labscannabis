# IndexNow: как повесить пинг на деплой

**Кому:** владельцу. Кода писать не нужно, всё уже написано.
**Что это даёт:** после каждого выката Bing, Яндекс, Naver, Seznam и Yep получают
список всех страниц сайта и приходят перечитывать их не «когда-нибудь», а обычно
в тот же день.

## Сначала — чего это НЕ даёт

**Google в IndexNow не участвует.** Не участвовал никогда, и обещать обратное
нельзя ни в одном тексте: пинг не ускоряет индексацию в Google, не заменяет
Search Console и не влияет на позиции в Google вообще никак. Для Google
единственный программный канал — Search Console API, он описан отдельно в
[`04-search-console-api.md`](./04-search-console-api.md).

Стоит ли тогда возиться? Да, по одной причине: русский запрос про Паттайю в
Яндексе — это не остаток трафика, а вторая по величине аудитория магазина, и
Bing отдаёт часть англоязычного. Обе системы IndexNow поддерживают.

## Как это устроено сейчас

Скрипт — `scripts/ping-indexnow.mjs`. Три свойства, которые важно знать:

1. **Список URL он берёт из собранного `sitemap-index.xml`**, а не из списка
   внутри себя. Появилась новая страница — она попадает в пинг сама. Забыть
   дописать её некуда, потому что дописывать нечего.
2. **Он не входит в `npm run build`.** Это не мелочь: CI после сборки делает
   `git diff --exit-code`, то есть сборке запрещено менять хоть один файл в
   репозитории, и любой шаг, который лезет в сеть во время сборки, рано или
   поздно её роняет. Пинг живёт отдельно и запускается ПОСЛЕ выката.
3. **Он не роняет деплой.** Недоступный эндпоинт, 403, таймаут, отсутствующий
   `dist/` — предупреждение в лог и выход с кодом 0. Сайт уже выложен; не
   принятый пинг означает только то, что переобход придёт своим чередом.

Ключ владения — файл `public/7c4e9b2a1f8d46e3b0c5a7d9e1f24368.txt`, внутри
которого написано то же самое, что в имени. Так участники протокола убеждаются,
что пинг шлёт владелец домена. Скрипт проверяет совпадение ДО отправки, потому
что иначе 403 в логе выглядит как «непонятная ошибка сети».

Проверить, что всё на месте, можно прямо сейчас и без отправки:

```
npm run build
node scripts/ping-indexnow.mjs --dry-run
```

Скрипт напечатает host, адрес ключа и все URL, которые ушли бы в пинг.

## Способ 1 (рабочий, уже настроен): GitHub Actions по событию от Vercel

В репозитории лежит `.github/workflows/indexnow.yml`. Он срабатывает на событие
`deployment_status` со статусом `success` — это то самое событие, которое Vercel
через свою интеграцию с GitHub присылает, когда новая версия УЖЕ доступна по
боевому адресу. Затем workflow собирает сайт (сайтмапа в репозитории нет, он
появляется только после сборки) и отправляет пинг.

Ничего включать не нужно, если интеграция Vercel↔GitHub стоит по умолчанию.
**Как убедиться, что работает:** после ближайшего выката открыть на GitHub
вкладку **Actions** → workflow **Notify search engines**. Должен быть запуск, а
в нём шаг «Show trigger» с `state=success` и строка вида
`[indexnow] ответ 200 — принято`.

**Если запусков нет вообще** — значит, Vercel не создаёт GitHub-деплойменты для
этого проекта. Тогда либо включить это в настройках интеграции Vercel для
репозитория, либо взять способ 3.

Запустить руками в любой момент: **Actions → Notify search engines → Run
workflow**. Галочка «dry run» напечатает список URL и ничего не отправит.

## Способ 2: вебхук Vercel «Deployment Succeeded»

Vercel умеет присылать вебхук на успешный деплой. Это правильное событие: оно
приходит, когда версия уже выложена.

Честная оговорка: **на каком тарифе Vercel доступны вебхуки и создаются ли они
на уровне команды или проекта — я проверить не смог** (документация Vercel из
рабочей среды недоступна). Смотреть в самой панели: **Settings → Webhooks**. Если
раздела нет — способ не подходит, берите способ 1 или 3.

Даже когда вебхук доступен, ему нужен адрес, который его примет и запустит
скрипт. Самое простое — направить его на `repository_dispatch` GitHub, который
запустит тот же workflow. То есть способ 2 всё равно упирается в способ 1, но
через лишнее звено. **Отдельной ценности он не даёт, рекомендовать его не за
что.**

## Способ 3 (если GitHub Actions недоступны): Vercel Cron

Раз в сутки дёргать пинг по расписанию. Годится как страховка: список URL берётся
из живого сайта, а не из момента выката, так что «опоздать» тут нечем — просто
поисковик узнаёт о новых страницах не в день выката, а в пределах суток.

Требует serverless-функции в проекте, которой сейчас нет ни одной, — то есть
это осознанное расширение периметра, а не настройка галочкой. Пока способ 1
работает, трогать не нужно.

## Чего делать НЕЛЬЗЯ

**Не вписывать пинг в Build Command в Vercel.** Соблазн понятный — одна строка в
настройках. Но команда сборки выполняется ДО того, как новая версия становится
доступна по боевому адресу. Поисковики придут на предыдущую версию сайта: для
изменившихся страниц это бессмысленно, а для новых — прямо вредно, потому что
краулер получит 404 и следующий заход отложит.

**Не вписывать пинг в `npm run build`.** См. пункт 2 выше: CI проверяет, что
сборка не меняет репозиторий, и требует, чтобы `npm run build` был
детерминированным и офлайновым.

## Что смотреть потом

Bing Webmaster Tools и Яндекс.Вебмастер показывают, приняли ли они пинг и что
переобошли. Дальше начинается обычное: приняли пинг ≠ проиндексировали. Пинг
управляет только скоростью визита краулера, а решение об индексации принимается
по качеству страницы — за это отвечают ворота качества в
`scripts/lib/quality-gate.mjs`, а не этот скрипт.
