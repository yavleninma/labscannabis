# Google Search Console API: что должен сделать владелец

**Кому:** владельцу. Программировать не нужно — нужно нажать кнопки в двух
сайтах Google и вставить одну длинную строку в Vercel. Займёт минут двадцать.

**Состояние на сегодня:** код готов и лежит в `scripts/gsc-submit.mjs`. Ключа
нет, поэтому скрипт при запуске честно печатает «не настроен» и выходит без
ошибки. Ничего не сломано и не ждёт починки — просто канал к Google пока
выключен.

---

## Зачем это, если сайт и так в Google

Ради одной цифры. В выгрузке Search Console по этому домену **149 URL в статусе
«Обнаружена, не проиндексирована»**. Это значит, что Google уже посмотрел на
массовые шаблонные страницы сайта и отказался брать их в индекс. Не «ещё не
дошёл» — именно отказался.

Пока мы не можем спросить Google программно, любые рассуждения о том, помогают
ли новые страницы, — вера. API даёт замер: по каждому URL Google возвращает свой
вердикт и причину. Тогда ворота качества (`scripts/lib/quality-gate.mjs`) можно
сверять с реальностью: страница прошла ворота — а Google согласился?

Второе, помельче: скрипт сообщает Google, что карта сайта обновилась. Это ровно
та же кнопка, что в интерфейсе Search Console, только автоматически после
каждого выката.

## Чего API НЕ умеет — чтобы не ждать зря

- **Отправить страницу в индекс нельзя.** Такого API у Google нет. Есть Indexing
  API, но он официально принимает только вакансии и трансляции; для магазина он
  не предназначен, и сервисы, которые обещают им «мгновенную индексацию», врут.
- **Ускорить индексацию нельзя.** Отправка карты — это уведомление, а не
  просьба. Инспекция URL вообще только читает.
- **Заменить IndexNow нельзя, и наоборот тоже.** Google в IndexNow не участвует;
  Яндекс и Bing не читают Search Console. Это два разных канала к разным
  поисковикам, оба нужны.

## Шаг 1. Завести проект в Google Cloud

1. Открыть <https://console.cloud.google.com/> под **тем же аккаунтом Google, под
   которым открывается Search Console магазина**. Это важно — иначе на шаге 4 вы
   не найдёте, куда добавлять доступ.
2. Вверху слева, рядом со словом «Google Cloud», нажать на выпадающий список
   проектов → **New project** (Новый проект).
3. Имя — любое понятное, например `labs-search-console`. **Create**.
4. Дождаться, пока проект создастся, и убедиться, что вверху выбран именно он.

Денег это не стоит: Search Console API бесплатный, карта оплаты не требуется.

## Шаг 2. Включить Search Console API

1. В поиске вверху набрать **Google Search Console API**.
2. Открыть найденный результат и нажать **Enable** (Включить).

Если кнопка называется **Manage** вместо **Enable** — значит, API уже включён,
идём дальше.

## Шаг 3. Создать сервисный аккаунт и скачать ключ

«Сервисный аккаунт» — это робот со своим адресом электронной почты, от имени
которого работает скрипт. Так вашему личному аккаунту Google не нужно нигде
светиться, и отобрать доступ можно у робота, не трогая себя.

1. Меню слева → **APIs & Services** → **Credentials** (Учётные данные).
2. Сверху **Create credentials** → **Service account**.
3. Имя — например `labs-gsc-bot`. **Create and continue**. Роль в Google Cloud
   спрашивать могут — **никакой роли выдавать не нужно**, нажать **Continue** и
   потом **Done**. Доступ выдаётся не здесь, а в Search Console на шаге 4.
4. В списке появится строка с адресом вида
   `labs-gsc-bot@labs-search-console.iam.gserviceaccount.com`.
   **Скопируйте этот адрес — он понадобится на шаге 4.**
5. Нажать на эту строку → вкладка **Keys** → **Add key** → **Create new key** →
   формат **JSON** → **Create**.
6. В браузер скачается файл вида `labs-search-console-a1b2c3.json`.

> **Этот файл — ключ от доступа.** Не класть его в репозиторий, не отправлять в
> мессенджере, не выкладывать в облако с общей ссылкой. Если он всё-таки куда-то
> утёк — вернуться в **Keys**, удалить ключ и создать новый; старый мгновенно
> перестанет работать.

## Шаг 4. Дать роботу доступ к ресурсу в Search Console

Это тот шаг, который забывают, и потом весь день видят ошибку 403.

1. Открыть <https://search.google.com/search-console/>.
2. Слева вверху выбрать ресурс сайта. **Запомните, как он там записан**, это
   понадобится на шаге 5. Возможны ровно два написания:
   - `https://labscannabis.boutique/` — ресурс типа «префикс URL» (со слэшем на
     конце);
   - `labscannabis.boutique` с пометкой «Домен» — ресурс типа «Домен».
3. Слева внизу **Настройки** → **Пользователи и разрешения**.
4. **Добавить пользователя**. Вставить адрес робота со шага 3.4.
5. Разрешение выбрать **Владелец**.

Про «Владельца» отдельно: для отправки карты сайта хватило бы разрешения
«Полный», но инспекция URL сервисному аккаунту без прав владельца отвечает
отказом. Раз уж заводим — сразу владельцем, иначе половина смысла пропадает.

Если Google не даёт выбрать «Владелец» прямо в этом окне, значит, у ресурса
владелец подтверждается отдельно: нажать на своё имя владельца в том же разделе
→ **Управление владельцами ресурса** → **Добавить владельца** и вставить адрес
робота туда.

## Шаг 5. Положить ключ в переменные окружения Vercel

1. Открыть скачанный на шаге 3 JSON-файл **обычным текстовым редактором**
   (Блокнот, TextEdit, VS Code — любой). Не Word.
2. Выделить **всё содержимое целиком**, от первой `{` до последней `}`, и
   скопировать. Ничего не подправлять руками — длинные строки с переносами так и
   должны выглядеть.
3. Открыть <https://vercel.com/> → проект сайта → **Settings** → **Environment
   Variables**.
4. Создать переменную:
   - **Name:** `GSC_SERVICE_ACCOUNT_JSON`
   - **Value:** вставить скопированное содержимое файла
   - **Environments:** отметить **Production** (Preview и Development не нужны)
   - если предлагается пометить значение секретным / скрытым — пометить.
5. Если ваш ресурс в Search Console записан как **Домен** (шаг 4.2), добавить
   вторую переменную:
   - **Name:** `GSC_PROPERTY`
   - **Value:** `sc-domain:labscannabis.boutique`

   Если ресурс — «префикс URL», вторую переменную создавать не нужно: скрипт по
   умолчанию берёт `https://labscannabis.boutique/`.
6. **Save.** Переменные подхватываются на следующем выкате.

### То же самое для GitHub

Скрипт запускается после деплоя из GitHub Actions
(`.github/workflows/indexnow.yml`), поэтому ключ нужен и там:

1. GitHub → репозиторий → **Settings** → **Secrets and variables** → **Actions**.
2. **New repository secret**: имя `GSC_SERVICE_ACCOUNT_JSON`, значение — то же
   содержимое файла.
3. Если ресурс типа «Домен» — на вкладке **Variables** создать `GSC_PROPERTY`
   со значением `sc-domain:labscannabis.boutique`.

Больше ничего менять не надо: шаг «Submit sitemap to Google Search Console» в
workflow уже стоит и сегодня печатает «не настроен». В день, когда появится
секрет, он начнёт работать сам.

## Как проверить, что получилось

На своей машине, из папки проекта:

```
npm run build
GSC_SERVICE_ACCOUNT_JSON="$(cat ~/Downloads/labs-search-console-a1b2c3.json)" npm run seo:gsc -- --list
```

Правильный ответ выглядит примерно так:

```
[gsc] ресурс         https://labscannabis.boutique/
[gsc] сервисный аккаунт labs-gsc-bot@labs-search-console.iam.gserviceaccount.com
[gsc] токен получен
[gsc] отправляю sitemap  https://labscannabis.boutique/sitemap-index.xml
[gsc] sitemap принят (200)
```

### Если вместо этого ошибка

| Что в логе | Что это на самом деле |
| --- | --- |
| `не настроен` | Переменная не долетела до скрипта. Проверить имя: `GSC_SERVICE_ACCOUNT_JSON`, ровно так. |
| `type="..." а нужен "service_account"` | Скачан не тот файл. Нужен JSON из раздела **Keys** сервисного аккаунта, а не файл OAuth-клиента. |
| `не похожа ни на JSON, ни на base64` | В переменную попал кусок файла или путь к нему. Нужно содержимое целиком, начиная с `{`. |
| `invalid_grant` | Ключ удалён в Google Cloud или сервисный аккаунт стёрт. Создать ключ заново (шаг 3.5). |
| `403 — у сервисного аккаунта нет доступа` | Пропущен шаг 4, либо `GSC_PROPERTY` записан не так, как ресурс в консоли. Это две разные ошибки с одним кодом, проверять обе. |
| `404 — ресурс ... не найден` | Написание ресурса не совпадает. `https://…/` со слэшем — для префикса URL, `sc-domain:…` — для домена. Третьего варианта нет. |

## Что этим можно делать дальше

```
npm run seo:gsc                       # отправить карту сайта
npm run seo:gsc -- --list             # что Google уже принял и сколько взял в индекс
npm run seo:gsc -- --inspect https://labscannabis.boutique/en/strains/gelato/
npm run seo:gsc -- --inspect-sample 30   # выборка по всем локалям равномерным шагом
npm run seo:gsc -- --dry-run          # показать, что было бы сделано, не трогая сеть
```

Полезнее всего третья и четвёртая. Выборка печатает по каждому URL состояние
Google, а в конце — сводку. Строка `Discovered - currently not indexed` в этой
сводке и есть те самые отказы: **это не очередь, это отказ**. Если после
очередной волны страниц их число выросло — волна была лишней, и её надо не
дописывать, а сокращать.

**Квоты.** Инспекция ограничена 2000 запросами в сутки и 600 в минуту на ресурс.
Скрипт держит паузу между вызовами и не даёт запросить больше 200 URL за раз, но
гонять `--inspect-sample` в цикле всё равно не нужно: раз в неделю после выката
достаточно.
